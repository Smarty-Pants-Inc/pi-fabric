# NATS host-local presence projection

With `mesh.transport: "nats"`, each local `ParticipantDirectory` projects only its authenticated transport machine's current participant and host-lease KV rows into the ordinary local files. The projection is one-way: NATS KV remains authoritative; these files are a local compatibility/read model, not a second source of truth. `mesh.transport: "file"` does not create the projection.

## Snapshot, updates, and recovery

The projection watches only `<machine>.p.>` in `presence` and `<machine>.h.>` in `leases`. It never copies another machine's KV rows. It writes participants through `writeParticipantFileIf` and leases through `writeHostLease`, preserving the established local file formats and the readers that already consume them. Projected records carry private `natsProjection` provenance (machine, KV key, owner, incarnation, and KV revision) so a delayed writer or removal cannot replace or delete a newer owner/version. An unchanged participant payload advances only its persisted provenance revision. Lease payload refresh is coalesced until the local file's expiry is within half of the 15-second host-lease TTL, while its provenance revision advances on each KV update so another projection can fence a delayed tombstone.

NATS KV watchers deliver a current snapshot followed by live changes; the NATS documentation describes the initial snapshot and the null/end marker that separates it from subsequent updates ([Key/Value Store](https://docs.nats.io/nats-concepts/jetstream/key-value-store), [JetStream KV developer guide](https://docs.nats.io/using-nats/developer/develop_jetstream/kv), [watching keys](https://docs.nats.io/nats-concepts/jetstream/key-value-store/watch)). The transport adapter exposes the snapshot boundary as `ready` and recovery as `reset`. A reset causes a fresh snapshot; after each snapshot, local projection entries not observed are checked with a KV `get` before cleanup. A read error is not treated as absence. Before applying a tombstone, the projector also re-reads that exact KV key: if a delete-and-recreate has already produced a current row, it reprojects the row and leaves the file in place; a failed read retains the file and restarts that bucket from a fresh snapshot. A processing or local-file error after initial readiness restarts only that bucket with bounded exponential backoff (100 ms up to 5 seconds), and the replacement watch snapshots and reconciles before resuming updates. Tombstones remove only a local file whose provenance still identifies the removed key and has not advanced past its revision. The projector retains no process-lifetime per-key revision table: the adapter restarts with a fresh ordered snapshot after gaps, while file provenance and exact-key reads fence stale events. Its key-to-file indexes are rebuilt from extant local projections at each snapshot and dropped on tombstones; the lease stat cache is pruned to extant local host-lease files. Startup, watch recovery and tombstones therefore converge without treating a local file as authority.

A reader that observes both the live NATS view and its local projection must use the current KV row as the authority; it does not let a local timestamp outrank KV. Both copies originate from that same row, so their participant payload, owner incarnation, and source `updatedAt` agree. Readers that merge a local file with its keyed shared-state copy keep the existing rule unchanged: the later `updatedAt` wins and the file wins a tie; a bridge/mirrored state row never outranks a native file. No reader or FILE-transport behavior is changed.

## Operations and rates

`ParticipantDirectory.natsProjectionMetrics` is available only for NATS mode. It identifies the credential-bound `machine` and reports cumulative participant/host-lease file writes (including removals), local reconciliation reads (snapshot/removal scans, write decisions and lease-cache stat checks), KV reconciliation/tombstone-fence `get` calls, elapsed time, and each count normalized to a per-minute rate. An operator can sample these values once per host to separate steady lease renewal from churn or a recovery resnapshot.

The deterministic one-host rate tests use an injected monotonic fixture clock and exercise a 60-second steady sequence: participant writes 4/min, host-lease writes 13/min, participant-file reconciliation reads 5/min, host-lease reconciliation reads 14/min (the snapshot scan, initial write, and twelve locked renewal/provenance updates). The fixture sends lease updates every five seconds; host-lease payload expiry refresh still occurs at ten-second intervals, while provenance-only file writes advance the marker on each KV revision. A separate 60-second one-host churn window with three additions and one removal reports 5 participant mutations/min, 5 host-lease mutations/min, 6 participant reconciliation reads/min, 7 host-lease reconciliation reads/min, and 2 KV reconciliation/tombstone-fence reads/min. These are deterministic fixture rates, not a claim of measurements on a live NATS host; the metrics expose the corresponding live per-host measurements.
