# Windows mesh lock release

Issue: smarty-dev#9569. This is the **release slice**, not a whole-root Windows safety claim. Acquisition recovery, legacy canonical-debris repair, the mixed-version gate fixture and macOS characterization are a separate change. Do not advertise the stronger root-wide guarantee until those gates pass.

## Release contract

A Windows holder prepares a digest-pinned native capability **before publishing its owner**. The release closure retains that capability and the original complete owner record. There is no Windows pathname-rename or recursive-delete fallback when the helper is unavailable.

The native release checks exact directory and owner identities, owner bytes, ownership and location while holding the directory without delete sharing. A canonical lock must initially contain exactly `owner`; an extra or unknown entry refuses release with the owner intact. The helper closes the verified owner read handle, but keeps the directory guard, then renames the **held directory object** to the same-parent `r.<64hex>` name without replacement. This rename is the commit point. Only afterward may it dispose the verified owner by handle and remove the retired directory if empty. Cleanup never resolves the canonical lock again.

A late unjudged child is not deleted. It may leave a reported retirement sibling, but it cannot block the next canonical acquisition. Foreign collision targets are not replaced or removed; an existing exact original retirement receipt may be reconciled as described below. Linux's directory-fd-pinned release is unchanged. macOS retains its weaker pathname-based behavior: this change does **not** provide Mac parity.

## Outcomes and application errors

A terminal native result distinguishes `not-owner`, `released` (clean or cleanup pending), and `refused-before-retirement`. The caller additionally distinguishes a helper that is unavailable before start from `release-outcome-unknown`: a started child without a valid terminal result **and** matching process exit might already have committed the rename. Empty output, a timeout or a nonzero exit is not proof that nothing happened.

After joining an unknown child, the caller may make one bounded reconciliation attempt using the **identical original framed request**, including original directory and owner snapshots, full record and retirement destination. It does not resnapshot a successor or infer completion from an absent canonical name. It never replays the application operation. A surfaced `MeshLockReleaseError` has code `FABRIC_MESH_LOCK_RELEASE_FAILED`, explicit operation and release states, `retryable: false` for application replay, and `retryRelease()` for release only. `operationCompleted` means the operation returned; an operation that threw may still have side effects. A primary operation error stays primary, even for non-Error throws; release failures are secondary and observable. Nested fences attempt both releases.

## Same-record reconciliation after interruption or parent death

A repeated native request first opens its deterministic retirement destination with DELETE access and no delete sharing. It verifies the **original directory identity**, real-directory kind, SID and final location under held ancestors before any cleanup. Only confirmed absence permits the ordinary canonical release path. A different directory, reparse point, occupied foreign target or unreadable target fails closed. An authenticated retired directory resumes the existing W5 cleanup; this branch never opens the canonical lock, even if B now owns it.

W5 requires the full original owner bytes and exact owner identity, time and size before deleting that owner by handle. Alternatively, the held original directory must genuinely be empty, in which case no file is deleted. A rediscovered empty receipt uses zero owner ids/time (the request still contains full R and its length); if an owner appears before native inspection, that request has no file-delete authority. Empty-only directory disposition preserves any late unjudged entry. Extra, foreign, torn or otherwise unverified content is retained and reported pending/refused, never recursively removed. The existing watchdog and per-mutation deadline checks apply to resumed cleanup too; every child remains bounded and joined.

Parent death loses the JS request. An **explicit release-only call with the original full record** can rediscover it without a cache, background collector or new durable file protocol. Only when canonical state is absent or its record differs does JS inspect the same parent nonrecursively with `opendir`, capped at 256 entries (at most 257 reads to prove completion/cap exhaustion). Normal matching canonical releases do not scan. A candidate must have the exact `r.<64 lowercase hex>` name equal to the existing hash of canonical basename, that candidate's bigint directory identity, and original full record. Arbitrary empty `r.*` siblings and nonmatching receipts are not candidates. Exactly one identity-bound real directory may be judged: a stable full original owner snapshot, or two empty observations of the same directory. Its contents are also boundedly inspected. Native still performs the authoritative held-handle checks.

Multiple matching receipts, an exhausted listing cap, changed proof or inaccessible state yields an explicit operator refusal before a child starts; nothing is guessed clean. A successful retry cleans only the original T, leaving B's full owner and both identities untouched. Repetition after T is gone returns `not-owner` without starting a child. This is original-receipt release authority, **not** PID/death-based reclaim authority for live, foreign or protocol-unproven records. Pending cleanup is not a claim that T was removed.

## Retained helper cache and package maintenance

The per-user, non-temp cache is outside the package's `dist/` tree. Each published digest directory contains one immutable helper build. A trusted packaged bootstrap (or an already established retained capability) checks exact bytes, regular-file/no-reparse status, real-directory ancestry and Windows owner/DACL privacy before that executable is used. An unvetted cache executable must never validate itself.

New versions publish from private staging without overwriting an existing digest directory. Concurrent publishers verify the winner. A running holder captures its exact absolute path, digest and mesh ABI; each spawn rehashes that path. Package rebuild, update and uninstall may remove package `dist/` but **must not remove published digest cache directories**. Old and new helper digests coexist. There is no automatic cache collector.

To collect the user-wide helper cache, first stop admission and automatic restart from **all roots and launchers** using that cache, drain all resident Fabric processes and holders, and join their terminal process exits. Only then may an independently authorized maintenance operation remove cache versions and restart admission. An empty canonical lock or a PID snapshot is not a global drain. A per-root writer drain is not sufficient for this user-wide cache operation.

Deleting or rewriting a retained digest during a live section is unsupported tampering or undrained maintenance. Release fails closed; restore the exact trusted bytes and use the same-record release retry, without repeating application work.

## Windows rollout gate and T11 runbook

**Starting an updated B while an old A is alive is not safe.** Every updated owner mutator follows the directory-guard rule, but an old pathname-based releaser does not. Installing a new runtime/helper, switching custody to `dual`, or selecting protocol 3 cannot constrain a paused old program. The stronger per-root guarantee remains withdrawn until the following gate completes. An empty lock, a capability check, an owner file disappearing, a PID snapshot, or a root-local marker is not a drain receipt.

### 1. Close admission and inventory the exact root

Record the normalized absolute root, volume/file identity, account and filesystem, plus the change owner. Verify that the root and its ancestry are the intended real directories, not aliases/reparse points. Inventory **all known paths that can launch or retain a writer for this root**: services, scheduled tasks, supervisor/restart policies, resident Pi/Fabric sessions, interactive terminals, child launchers, migration/maintenance tools, custody writers, queued waiters, paused recoverers, and synchronous fence/open paths. Include launchers that currently have no lock and holders that currently have no canonical owner file.

For each launcher record its controller, enabled/auto-restart state, exact installed runtime/build path and digest, root arguments, and all resident process/descendant handles it owns. Stop admission and disable auto-start/restart at each launcher before beginning the drain; keep them disabled throughout installation and canaries. Inventory is an operational assertion by the controllers, not something a lock filename or this test discovers. If inventory/control is incomplete, keep the guarantee withdrawn and admission stopped. A newly exclusively controlled root is an alternative only after a separately authorized data handoff; do not silently move shared state to evade the gate.

### 2. Drain the entire old cohort and retain actual terminal receipts

Let outstanding work finish or stop it through its authorized controller. Include old holders, waiters, stalled/paused releasers, acquisition recoverers, synchronous writers and their descendants, not merely whichever PID is in `owner`. Join the actual owned process handles and retain terminal exit/status/time receipts for **every inventoried old process**, with controller confirmation that no replacement was started. A terminal application message is not process exit. Waiting for one parent does not prove its descendants ended; each controller must account for its full cohort.

Keep admission closed while any inventoried old process is alive or its terminal state is unknown. A failed stop, inaccessible process, lost process handle or newly discovered launcher returns the gate to closed/incomplete; do not infer death from a missing PID or from age. Preserve root identity and the inventory/terminal receipts with the release record. Do not delete or quarantine unknown lock state as a shortcut to draining a live writer.

### 3. Verify the installed candidate and run canaries before reopening

Install the exact approved build with launchers still disabled. Record the installed package location, build revision/artifact digests, Node/runtime executable digest and version, packaged helper digest/ABI, and the retained helper absolute path and observed digest used by each canary release. The retained path must be the content-addressed private cache capability captured by that holder, not a newly resolved package helper. Do not collect old published cache digests during this per-root rollout.

Run the public release/paused-successor and applicable recovery canaries against a **disposable, exclusively owned test root**, using the **installed package's** entry points, account and real Windows filesystem. Never force a replacement race in the production root. Require exact successor owner bytes/identities to survive stale release, a real contender to remain excluded until B releases, then a subsequent public acquisition to enter. Require joined real native release samples to report the installed helper digest and retained path; mocked success or a source-only import is not an installed canary. Run the separate recovery/native matrix for the applicable policies as well; T11 alone does not certify legacy-debris or every custody/fence route.

The executable T11 fixture is `tests/mesh-lock-windows-rollout.test.ts` with plain-Node child `tests/fixtures/mesh-windows-rollout.mjs`. It uses the **actual built** pre-fix source archive at `dcc0825cb005ebfc37c37514f159cdb3570281f4`, not a handwritten old release. The existing hosted `scripts/windows-mesh-release-baseline.ps1` builds that baseline once for T12, then sets `FABRIC_9569_ROLLOUT=1` and passes baseline/current project paths and exact revisions to T11 **before** running the unchanged T12 driver. Outside that explicit hosted Windows registration the suite declares an expected skip; missing inputs after registration fail. Local/Linux execution is not admitted or platform evidence.

T11 covers public `MeshStore.exclusive` protocols 1 and 2. Its controller owns the entire fixture cohort, including an actual old public waiter. It pauses the old public releaser after its real check, immediately before its actual pathname rename, with a pass-through filesystem checkpoint. A deliberately gate-bypassing new B is then destroyed by the actual old release on the fixture root: this is a required contained negative result, not a failed assertion waved away. Admission stays closed while the old cohort is alive; only actual terminal joins of **all** those old fixture processes admit the all-new canary. Updated A pauses after the real checks/retained-helper rehash and before the native guard; a public successor B survives A's actual native refusal, excludes C, then releases and permits another acquisition. Checks do not spoof native outcomes or replace death policy. Every Node child has a finite deadline, failure teardown opens all owned checkpoints and joins all children, and abnormal terminal outcomes fail and retain fixtures rather than deleting underneath an uncertain child.

Hosted receipts `t11-p1.json`, `t11-p2.json`, `t11-p*-terminal.json` (also written after assertion/checkpoint failure) and `rollout-probe.log` are retained beside the T12 results in `FABRIC_9569_PERF_RESULTS`. They record the pinned baseline/current revisions, public-entry/runtime/helper digests, actual native child samples, full old fixture-cohort terminal receipts, admission times and preserved successor identities. These prove the deterministic **owned fixture gate only**; they do not inventory or certify an unknown production root. The existing Windows baseline workflow step already invokes the script, so T11 needs no additional workflow registration. T12 still runs its identical baseline-then-candidate 100 serial + 4×25 contended operations even if T11 returns failure; a T11 failure still fails the script.

For an installed-build repetition in an authorized disposable hosted Windows job, retain the same real built baseline inputs, set `FABRIC_9569_ROLLOUT_CURRENT_PROJECT` to the absolute **installed candidate package** (with its `dist/mesh.js`, stable release observer and packaged native helper), set `FABRIC_9569_ROLLOUT_CURRENT_HEAD` to its verified build revision, retain `FABRIC_9569_ROLLOUT=1`, and run `bunx vitest run --retry=0 tests/mesh-lock-windows-rollout.test.ts` from the matching candidate test checkout. The independent packaged-digest check must match that installed build. Save the installed receipts separately from checkout-run receipts; a checkout canary is not represented as installed evidence.

### 4. Reopen only the verified updated cohort; rollback drains again

After complete old-cohort terminal receipts **and** installed canary/recovery evidence pass, restart only the inventoried launchers pinned to the verified updated build. Record each launcher's new path/digest, admission reopening time and root identity. The stronger root-wide claim begins only at that point, subject to the other release gates; adding this runbook/test is not evidence that a production rollout occurred.

Rolling back or introducing any old writer repeats admission closure, full-cohort drain/terminal joins and canaries. An old build withdraws the stronger guarantee even if its helper cache remains present. Re-enable no unknown auto-restart path. This gate is **per root**; user-wide native-cache collection remains the distinct **GLOBAL** maintenance drain described above, across every root/launcher sharing that cache.

## Protected historical state

Automatic cleanup may apply only to empty directories or records whose death is independently proven under the current namespace policy. Recordless nonempty, torn, live, foreign and unproven canonical state is never garbage merely because it is old or has a release-looking filename. Protocol-3 Windows PID evidence is not sufficient for reclaim.

Unknown canonical debris requires typed operator handling and a quiesced quarantine: stop and join affected writers, preserve a forensic snapshot, verify root identity and no reparse points, and obtain authority to quarantine the exact reported directory. Do not use an unattended recursive deletion. Sibling `r.*` and old `.released.*` artifacts do not gate a free canonical lock. Retained `.dead.<64hex>` recovery fences are not release garbage and must not be collected.

## Evidence gates

Hosted Windows CI on the exact PR head is required for actual sharing, handle rename/disposition, delete-pending behavior, process-kill partitions and the retained-capability update boundary. Linux skips are not Windows evidence. Report helper child-process p50/p95 and full-operation serial/contended measurements in the PR, without a flaky millisecond correctness threshold. The installed Ryzen 1 mesh smoke and independent acceptance audit remain delivery gates.

The logical normalized absolute mesh path must be under 240 UTF-16 code units, excluding only the Win32 namespace transport prefix and terminating NUL. Namespaced API arguments are measured separately; a longer API argument is not silently counted as a shorter logical path. No digest or ownership token is truncated to fit.
